# BotBound native window adapter

The companion invokes a fixed, packaged helper with one bounded JSON request over stdin. It never runs model-generated shell commands, AppleScript or JavaScript. Native helpers do not capture the desktop: the Electron main process supplies a capture of the exact selected window, identified by `nativeCaptureWindowId()`.

`native.ts` validates window identity and geometry before and after capture. Its observation fingerprint includes the window metadata and PNG bytes. A separate fixed activation operation brings the selected window forward before both the proposal capture and the final pre-input capture. Both observations therefore show the focused window; ordinary active/inactive title-bar changes do not invalidate every approval. Changed pixels after activation or loss of foreground reject execution. The input operation never activates a window. Helpers independently recheck the handle/CGWindowID, PID, process launch time, geometry, current foreground window and sensitive input target. Input acceptance is reported as `applied`; only a later observation can establish a task outcome. Interrupted or malformed execution responses become `unknown` and must not be retried automatically.

The exact PNG comparison is intentionally conservative: a blinking caret, clock, focus animation or other changed pixels may reject a valid proposed action and require a new observation. It has not been relaxed without real-device evidence. Two sequential text edits and ordinary browser navigation must be included in each OS acceptance run.

Coordinates are pixels in the returned screenshot. The adapter converts them to the selected window's current native bounds. Windows uses DWM extended-frame bounds and physical per-monitor-aware coordinates. macOS uses CGWindow bounds in global points. Windows wheel input approximates pixel distances with bounded wheel detents. Exact framing, scale, accessibility behavior and input targeting require interactive acceptance on each supported OS.

## Build

- Windows: install the official .NET 10 SDK, then run `node native/build.mjs --platform win32 --arch x64` from `apps/desktop`. `BOTBOUND_DOTNET_PATH` may name an absolute SDK executable. The output is self-contained; customers do not need .NET installed. `arm64` builds use `win-arm64`.
- macOS: use a Mac with Xcode command-line tools, then run `node native/build.mjs --platform darwin --arch arm64` (or `x64`). The target is macOS 13 or newer.

Each build writes `native/bin/<platform>/build-info.json` with the exact target architecture, source hash and binary hash. Distribution must validate these against its target, copy the matching helper into `resources/native/<platform>`, and sign the helper along with the application. A stale helper or a helper for another architecture is not a valid package. Build outputs are ignored.

## OS boundaries

- Windows runs `asInvoker`, without UIAccess or elevation. Secure/locked desktops, elevated targets, credential/settings windows and terminal/script-host processes are unavailable. It does not bypass UAC. A focused password field or inaccessible input target refuses input.
- macOS requires Accessibility permission for the signed helper/companion and screen-capture permission for Electron. The helper also checks event-posting authorization. It maps the selected CGWindow to exactly one public Accessibility window by title and bounds; ambiguous mappings refuse input. Terminal, credential and settings applications are unavailable.
- macOS text is sent in event payloads of at most 20 UTF-16 units without splitting surrogate pairs, with a focus/identity check before each chunk. Unsupported leading-newline chunks refuse the entire action before input; the helper does not replace them with Enter or hidden characters. Multiline text, emoji and app-specific input behavior need actual Mac acceptance.
- Mouse and keyboard actions run only against the approved foreground window. System-wide switching shortcuts are rejected. Ordinary application shortcuts still require the companion's owner task grant and action review.
- The adapter and helpers reject known launcher/desktop-switch key combinations and leading executable/local URL schemes. These are bounded safeguards, not an OS sandbox or a complete script detector. Renamed programs, custom web controls and application-specific shortcuts can hide behavior; browser canvas/custom credential fields may not expose password semantics to Accessibility. Owners must review each action and perform sensitive steps themselves. An unshared new window or dialog is never inherited as the selected target.
- Captures and native input are not invoked by unit tests. Windows compilation does not certify macOS compilation or either platform's live UI behavior. macOS signing, notarization, permission grant/revocation and actual input need a Mac acceptance run.

No input operation accepts executable paths, scripts, arbitrary file access or credentials. Stop/timeout terminates the bounded helper process and makes one bounded cleanup call to the same fixed helper. Cleanup only releases keys or a mouse button that the interrupted action could have pressed; it cannot refocus, move the cursor or replay the write. Normal helper exits also release incomplete input batches. Execution may already have begun, so its outcome remains unknown until reviewed. Force-quitting the entire companion, OS termination or a refused cleanup cannot guarantee input release; none is represented as a rolled-back action.

## Durable local receipts

The main-process store has a separate `commit_workspace` operation. It accepts only the trusted application-data directory and a generated `workspace-<UUID>.tmp` basename, and replaces the fixed `workspace.enc` target in that same directory. It accepts no file contents or arbitrary destination. Renderer, planner and native-action APIs do not expose it. It runs before capture/input permission checks so account saves do not require Accessibility permission.

The store flushes and closes the encrypted temporary file first. Windows then uses `MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH)` on a fixed local drive, without a copy/delete fallback; Node directory `fsync` is not assumed to work on Windows. macOS uses descriptor-relative replacement, synchronizes the workspace directory and its existing parent, then requires `F_FULLFSYNC` to flush the drive cache. Unsupported filesystem/flush behavior refuses the save. The store creates only its final directory, whose application-data parent must already exist.

No new memory state or action dispatch proceeds before the native acknowledgment. A failed temporary write/flush remains retryable. Once native replacement starts, any failed or missing acknowledgment freezes subsequent saves until restart, because the old or new file may have survived. A recovered claimed action becomes unknown and is never automatically replayed. These are OS persistence requests, not a claim to withstand failing hardware or storage that misreports flush completion. macOS compilation and real-device filesystem behavior still require Mac validation.
