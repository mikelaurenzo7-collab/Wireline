# BotBound authentication, redirect, callback, webhook, and deep-link launch checklist

**Audit date:** 2026-08-20

**Last reconciled with production voice runtime:** 2026-09-01

**Scope:** repository-defined contracts only; external dashboards and live environment values were not mutated or assumed to be correct.

**Launch target:** `https://botbound.me`; transitional legacy origin: `https://trywireline.com`.

## Executive launch decision

BotBound does **not** use Clerk or Supabase Auth. The active identity system is a custom Express/Postgres implementation: scrypt password hashes, locally minted HS256 JWTs signed by `INTERNAL_JWT_SECRET`, a host-only `wireline_session` HttpOnly cookie, and Google/Microsoft/Yahoo OAuth sign-in. Supabase is the PostgreSQL host; its Auth redirect settings are not in the request path. Sources: `DATABASE_SETUP.md`, `docs/security/auth-password-controls.md`, `src/lib/auth-service.ts`, `src/lib/session-cookie.ts`, `src/contexts/AuthContext.tsx`, `src/routes/auth-routes.ts`, and `src/routes/auth-oauth-routes.ts`.

The largest launch risk is **origin split**, not a missing auth vendor. `src/lib/brand.ts` and `docs/DEPLOYMENT_RUNBOOK.md` make `botbound.me` canonical, and the launch branch now aligns the web runtime, browser-extension package, and native-client source to that origin. Live Vercel environment values, provider dashboards, already-installed clients, and signed mobile/store binaries still require cutover proof. Because OAuth `redirect_uri`, the MCP issuer/resource, host-only cookies, and Twilio signature validation are origin-sensitive, a blanket HTTP redirect from the legacy host is not a safe cutover mechanism.

**P0 release gate:** add every `botbound.me` callback and webhook first, retain every required `trywireline.com` registration, set one coherent production `APP_URL`, redeploy, and run end-to-end tests on that same host. Keep exact callback paths served on the legacy host until logs prove no required traffic remains. Do not redirect an in-flight OAuth callback from one host to the other: the host-only OAuth/session cookies will not follow it.

**Support-email gate complete (2026-08-29):** `support@botbound.me` passed AgentMail DNS validation, external delivery to Gmail, a Gmail reply, and inbound receipt in the same AgentMail thread. Customer, legal, connector, and Stripe surfaces now use the BotBound address. Keep the legacy mailbox monitored only as a private compatibility fallback; transactional Resend bounce/complaint proof remains a separate gate.

## URL classes (do not mix them)

- **Browser redirect / OAuth callback:** a user's browser returns from a provider. It must match the provider registration and the `redirect_uri` used in both authorization and token exchange.
- **Server-to-server webhook:** a provider POSTs or GETs an event to BotBound. It is not a login redirect and must be authenticated with the provider-specific signature/secret.
- **Application return URL:** Stripe Checkout/Portal or an email link returns a user to the app; it is not an OAuth callback.
- **Allowed origin:** a browser security/CORS/CSRF boundary; it is not a redirect registration.
- **App/deep link:** an installed client route such as `wireline://calls`; it is not an HTTPS OAuth callback unless a provider is explicitly configured to use it.

## Clerk versus the actual architecture

### Recommendation: do not migrate to Clerk for launch

Clerk is now a credible architectural option, not just a conventional web-login replacement. Its current Express MCP guide supports OAuth protected-resource metadata, Clerk-issued token verification, and CIMD or Dynamic Client Registration for MCP clients. That makes it a strong post-launch candidate for consolidating browser identity and the MCP authorization-server surface. It is nevertheless a **higher launch risk than hardening the existing system now**:

1. BotBound user IDs already own tenant/RLS rows, provider tokens, Stripe customer/subscription state, phone bindings, MCP grants, and mobile sessions.
2. Browser auth is a host-only HttpOnly cookie with session-version invalidation; native clients use Bearer tokens; MCP adds a separate OAuth authorization-server bridge. Clerk would have to replace or coexist with all three.
3. The Google/Microsoft/Yahoo sign-in bridge has explicit verified-email, browser-binding, one-time-code, and session-generation behavior. A partial swap would create duplicate identity-linking paths.
4. Clerk's migration guidance warns that changing systems affects active sessions and requires user-ID/foreign-key mapping (often with `external_id`); staged/trickle migration introduces a dual-auth period. Clerk's webhook-sync guidance also notes eventual consistency and race conditions.

For launch, keep the current custom auth, finish the origin/callback cutover, rotate and verify secrets, run hostile redirect/state/session tests, and monitor auth errors. Immediately after launch, time-box a Clerk migration spike behind a feature flag rather than running a live dual-auth cutover. The spike must cover: threat model; user/tenant foreign-key map; `external_id` strategy; dual-session compatibility; native Bearer tokens; MCP client registration and scope parity; webhook/user-sync race handling; forced-session policy; rollback; and end-to-end billing/RLS/provider-token tests. Sources: [Clerk migration overview](https://clerk.com/docs/guides/development/migrating/overview), [Clerk's Express MCP guide](https://clerk.com/docs/expressjs/guides/ai/mcp/build-mcp-server), [Clerk OAuth behavior](https://clerk.com/docs/guides/configure/auth-strategies/oauth/how-clerk-implements-oauth), [Clerk webhook syncing](https://clerk.com/docs/guides/development/webhooks/syncing), and [OpenAI Apps authentication](https://developers.openai.com/apps-sdk/build/auth).

Supabase Auth is also technically viable because the database is already on Supabase and its OAuth 2.1 server now supports PKCE, OIDC discovery, Dynamic Client Registration, MCP authentication, and JWT/RLS integration. Its OAuth 2.1 server is currently labeled public beta, and BotBound's existing application-owned users and RLS context are not Supabase Auth users, so it is not a zero-migration shortcut. Evaluate it beside Clerk in the same post-launch spike; prefer Clerk for a managed identity/control-plane experience, or Supabase Auth if direct database-token and RLS convergence outweighs beta and migration risk. Sources: [Supabase OAuth 2.1 Server](https://supabase.com/docs/guides/auth/oauth-server), [Supabase MCP authentication](https://supabase.com/docs/guides/auth/oauth-server/mcp-authentication), and [Supabase OAuth setup](https://supabase.com/docs/guides/auth/oauth-server/getting-started).

## Ordered launch verification runbook

1. **Freeze the origin decision.** Production `APP_URL` must be exactly `https://botbound.me`; set transitional `CORS_ORIGINS=https://botbound.me,https://trywireline.com`. Never place a path or trailing slash in either origin.
2. **Attach and verify domains in the one canonical Vercel project.** Confirm `botbound.me` and the callback-compatible legacy origin resolve to the same intended production release, without an automatic redirect on callback/webhook paths.
3. **Print, diff, and register OAuth callbacks.** Run the callback printer for botbound, legacy, and localhost. Add botbound values without deleting legacy. Pay special attention to the shared Google (three paths), Microsoft (four), and Yahoo (two) clients.
4. **Reconcile MCP as one atomic issuer change.** The MCP URL, protected-resource metadata, authorization-server issuer, resource parameter, server card, ChatGPT/Claude/Cursor registration, privacy/docs links, and `APP_URL` must all name the same origin.
5. **Migrate server-to-server webhooks.** Stripe, Twilio number/SMS/voice/status/usage, OpenAI Realtime, Resend, each AgentMail mailbox, and Meta must be enumerated. Add or update BotBound endpoints and store each endpoint's matching signing secret. Remove retired xAI/Vapi/ElevenLabs callbacks instead of migrating them.
6. **Keep the proven support cutover coherent.** `support@botbound.me` passed the external round-trip and DNS gate on 2026-08-29. Keep the site, legal pages, connector listings, Stripe profile, and submission packets aligned to that address; retain the legacy mailbox only as a monitored compatibility fallback.
7. **Redeploy after environment changes.** Vercel environment changes do not alter already-built deployments.
8. **Test browser auth on botbound.** Password sign-up/verification/sign-in/reset/logout; Google/Microsoft/Yahoo sign-in; session refresh; Origin/Referer rejection; cross-host callback rejection.
9. **Test every connected integration.** Connect, one minimally scoped read/action where safe, token refresh, disconnect, reconnect. Record provider request IDs and callback host.
10. **Test payment returns and signed fulfillment separately.** Checkout and Portal landing pages are UX; signed `/api/stripe-webhook` delivery is the source of billing state.
11. **Test telephony using real signed traffic.** Exercise inbound SMS including STOP, Twilio-to-OpenAI SIP inbound, signed OpenAI `realtime.call.incoming`, approved outbound bridge/status/fallback, and message delivery statuses. Signature validation must use each exact public URL; an OpenAI failure must remain observable rather than switching voice providers.
12. **Test email webhooks.** Resend replay/duplicates and one AgentMail inbound message per migrated active mailbox.
13. **Audit legacy traffic.** Keep `trywireline.com` callback routes and secrets until provider dashboards plus production logs show zero required traffic for an agreed window. Only then remove registrations and redirect the retired public host.
14. **Release client surfaces separately.** The extension archive and native source are canonical-origin ready, but existing installs and mobile/store binaries are independent release artifacts. Ship and test each signed package before removing legacy API compatibility.
